:class:`~filelock.StrictSoftFileLock` creates ``<path>.filelock`` and its ``claims`` directory with the lock's ``mode``,
reaches ``claims`` through a descriptor opened without following symlinks (on Windows, holding both directories open
and refusing a junction), and refuses a coordination directory belonging to another account under a sticky parent such
as ``/tmp``; :class:`~filelock.SoftReadWriteLock` refuses such a ``<path>.rw`` too. Both directories get the sticky
bit, and one this account owns that is wider than the mode, such as one an earlier release created, is narrowed on the
next acquisition; a directory of another account is left as it is, so remove such leftovers from earlier releases by
hand. A claim scan waits out unreadable claims for one shared grace instead of one per claim, a failed claim cleanup
no longer leaves the sentinel descriptor open, and a non-regular node at a sentinel private-record name raises
:class:`~filelock.SoftFileLockProtocolError`. On Windows, contenders read claims without blocking their owner's unlink,
so a release no longer fails with ``PermissionError`` while another process is still reading the claim.
